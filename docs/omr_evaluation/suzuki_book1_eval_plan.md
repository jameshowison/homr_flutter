## Evaluation harness

**File:** `integration_test/suzuki_book1_sweep_test.dart`

- One `testWidgets` per case; 700 s per-case timeout.
- Loads image → runs `OmrOrchestrator().recognise()` with a 600 s inner
  `Future.timeout` → parses output MusicXML → compares against ground-truth
  XML using positional note matching (same logic as `benchmark_omr_test.dart`).
- **No pass/fail assertions** — data collection only.
- Prints one TSV row per case prefixed `RESULT\t`:

```
RESULT  label  notes_out  notes_ref  pitch_pct  dur_pct  both_pct  total_ms  timed_out
```

- Cases where the image file is missing produce `RESULT…SKIP`.
- Cases where the pipeline exceeds 600 s produce `timed_out=true`; the test
  continues without failing.
- Wall time > 180 s is flagged `⚠ slow` in console but does not fail.

## Known issues / open questions

1. **Gavotte accuracy vs violin XML:** Phone photo of Gavotte scores 21.4%
   against `17-gavotte.xml` despite detecting the right note count (193 vs 192).
   The existing benchmark scored 97.9% against Python homr output. This implies
   the abc2xml violin ground truth and homr's output disagree on pitch/duration
   representation. Needs investigation before drawing conclusions from Gavotte
   rows.

2. **Titles in crop images:** All `_crop.png` files include the song title at
   the top of the page. The existing benchmark uses title-excluded crops. Title
   content may confuse staff detection (phantom staves). This is intentional for
   this sweep — it tests the pipeline on realistic "full page" inputs.

3. **Parsing branch Gavotte timeout:** `homr-staff-parsing-experiment` timed out
   on Gavotte (306 s) in the prior session. With the 600 s per-case budget it
   will complete but be flagged `⚠ slow`. Task #9 (EOS early-stop / FFI
   overhead) would fix this.

4. **15-minuet-no-3 — spurious rest after dotted-half in bar 8 (pitch 29.1%):**
   Bars 1–7 and 9–32 are perfect. Bar 8 should be: grace note B4 + dotted-half
   A4 (filling 3/4). The pipeline correctly recognises the grace note and the
   half note, but emits an extra rest token after A4, giving `B4(eighth)
   A4(half) R` instead of `B4(grace) A4(dotted-half)`. The extra rest inflates
   the note count to 128 vs 127 reference and cascades all positional
   comparisons from bar 9 onward — the source of the low score.

   Root cause: a rest that fills 3/4 with a single dotted-half note is musically
   invalid (a dotted half *is* the whole bar; there is nothing left to fill).
   This is a musical-knowledge gap in the assembler or transformer post-
   processing: it should be impossible to emit a rest that would exceed the
   bar's remaining capacity. **Also applies to 09-perpetual-motion** (bar 8 has
   a spurious rest causing the +1 note count there too).

   Note: the ground truth XML was also wrong (`A5` → `A6` in the ABC source,
   `type=eighth duration=300` → `type=half duration=360 <dot/>` in the XML).
   ABC bug reported separately; patch at
   `docs/omr_evaluation/abc_bug_15_minuet_no_3.patch`.

   **Python homr does NOT have this problem.** Its token stream for bar 8 is:
   `note_8G B4 … note_2. A4 … barline` — grace note + dotted half, no rest.
   Python homr output XML: `<grace/> B4` + `<half><dot/> A4`. Correct.

   The Dart assembler correctly parses `note_2.` (`_kernToDuration("2.")` →
   `base=2, dots=1`), so the bug is likely upstream: the Dart dewarped strip
   fed to the transformer differs slightly from Python's, causing the transformer
   to emit `note_2` (plain half) + a rest token instead of `note_2.`. The
   assembler then fills the remaining 0.5 beats with a rest, producing an
   invalid bar (0 + 2 + 0.5 = 2.5 beats ≠ 3).

   For the agent picking this up: add token-stream logging to the Dart
   transformer runner for bar 8's staff strip and compare against the Python
   homr token stream (`note_2. A4`) to confirm whether the dot is being dropped
   by the transformer or by something else. Also: the assembler should reject
   bars whose filled duration exceeds or cannot reach the time-signature total —
   a rest that would make a bar exceed 3/4 is musically invalid and should be
   refused.

5. **09-perpetual-motion — octave error in bars 7–9 (pitch 45.3%):**
   Bars 1–6 and 10–16 are perfect (note names and octaves correct). Bars 7–9
   are read one octave too high throughout (e.g. A5→A6, G#5→G#6, F#5→F#6).
   Bar 8 also has a spurious rest, giving 129 notes vs 128 reference; the
   positional comparison then cascades mismatches across bars 7–9.

   Root cause: the pipeline mis-assigns the octave for one or more staff strips
   in the middle of the page. In standard treble clef the C-line position is
   fixed for the entire piece (no clef change occurs in Perpetual Motion); the
   octave of every note is derived from its pixel distance above/below that C.
   If the C-line reference is computed incorrectly for a strip, all notes in
   that strip land one octave off. This is a basic music/notation knowledge gap
   in the octave-assignment logic — **not** a key-signature issue (sharps are
   rendered correctly throughout).

   For the agent picking this up: investigate how the pipeline determines the
   C4 (middle-C) reference line for each staff strip, and why that calculation
   goes wrong for strips 2–3 of this image but not strips 0–1 or 4+.

5. **10-allegretto — pipeline crash fixed; accuracy still low:**
   Crash was in `_resampleSegment` (`staff_detection.dart:613`). `nonNullIdx`
   was built once from all non-null `axisCenter` entries, but the loop body
   could null out `nonNullIdx[k+1]`, causing the next iteration's `!` to crash.
   Fix: guard with `if (a == null || b == null) continue` before using `!`,
   which also correctly skips already-blanked entries (matching homr's
   "consecutive *present* centers" semantics). **Fixed 2026-06-06.**

   After fix: 92/94 notes found, pitch=40.2%, dur=51.1%, both=29.3%. Low
   accuracy puts it in the same bucket as Perpetual Motion and Minuet No. 3 —
   likely the same octave-assignment issue, not a separate bug.
